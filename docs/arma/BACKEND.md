# Arma 3 backend: spec -> mission folder

Status: groundwork. Implemented and unit-tested, **not flown**. Nothing generated by it has run in
Arma yet. The Hill (`arma/missions/dms_the_hill.Altis`) is still hand-tuned and remains the source
of truth until it plays well ([PLAN](PLAN.md), [ADR 0012](../adr/0012-multiple-game-backends.md)).
The backend is built alongside it and replaces nothing.

Code: `packages/dms-arma` (`dms_arma`). Command: `uv run dms-arma`.

## How it works

```
spec.yaml ──load_spec──▶ ArmaMissionSpec ──emit_config──▶ functions/fn_config.sqf
                              ▲                                   │
     fn_config.sqf ──parse_config──▶ dict ──spec_from_config──────┘ (inverse, for import)

build_mission(spec, template, out):
  copy template mission folder ─▶ out/
  overwrite out/functions/fn_config.sqf with the emitted config
  run KB + template checks
```

| Step | Module | Notes |
|---|---|---|
| Spec | `spec.py` | Pydantic, `extra="forbid"`, every field described. One section per fn_config block: `sites`, `squad`, `compound`, `enemy`, `qrf`, `artillery`, `exfil`, `test`. snake_case fields, typed ranges (`[min, max]` checked), bearings in `[0, 360)`, skills limited to real `setSkill` names. Class names must be identifiers, so nothing can inject SQF through a class field. |
| Emit | `config.py`, `sqf.py` | Deterministic: same spec gives the same bytes. LF, tab indent, header says GENERATED. Strings are double-quoted with `"` doubled (SQF escaping). Integral numbers have no decimal point, and exponent form is never written. Arrays break one element per line past 130 columns. Key order matches the hand-written file. |
| Parse | `sqf.py` | Parses the literal subset `fn_config.sqf` uses (numbers incl. hex, both string quote styles, booleans, arrays, comments, optional `createHashMapFromArray`). It rejects anything else, plus trailing commas and duplicate keys. `sqf_equal` compares values semantically (`8 == 8.0`, `true != 1`). |
| Import | `spec_from_config` | Rebuilds a spec from a parsed config. A key the spec doesn't cover, or a missing key, is an error, so a new tunable in The Hill fails loudly instead of being dropped. |
| KB checks | `kb.py` | Class names are checked against `docs/arma/kb/classes-verified.md`, and a class that isn't listed is **unverified** (a warning, or an error with `--strict`). BIS/BIN functions in every `.sqf/.ext/.hpp/.sqm` of the built folder are checked against `functions.txt`, and an unknown one is an **error**. |
| Template checks | `mission.py` | The `DMS_site` param in `description.ext` must offer exactly as many sites as the spec has. |

```bash
uv run dms-arma import arma/missions/dms_the_hill.Altis/functions/fn_config.sqf -o my.yaml
uv run dms-arma validate my.yaml [--strict]
uv run dms-arma emit my.yaml -o fn_config.sqf
uv run dms-arma build my.yaml --template arma/missions/dms_the_hill.Altis --out <dir>/dms_x.Altis
```

`build` refuses to write into the template folder. Point `--out` outside `arma/missions/`.

`packages/dms-arma/examples/the_hill.yaml` is The Hill's spec, produced by `dms-arma import`.

## Round-trip with The Hill

`tests/test_arma_roundtrip.py` parses the live `fn_config.sqf`, rebuilds the spec, emits it, parses
the result, and asserts there is no semantic difference and the key order is identical. It also
asserts that every `DMS_cfg get "<key>"` in the mission's scripts is a key the spec covers.

Differences between the generated and hand-written file:
- **Comments and layout are regenerated.** The hand-written explanatory comments (verification
  notes, building-position counts, "TO VERIFY" remarks) are replaced by shorter section comments.
  The values are identical.
- Numbers authored as `5.0` would be written as `5`. That is the same SQF scalar, and none exist
  today.
- `template`, `world` and `name` are spec-only. fn_config has no keys for them, so `import`
  takes them from `--world`/`--name`.

The example YAML is a snapshot. If The Hill is retuned, refresh it with the `import` command above.
The live round-trip test does not depend on the snapshot, so retuning never breaks it. Adding a new
key does break it, and that is intentional.

## What remains

1. **mission.sqm generation.** It is copied from the template today. The Hill's `mission.sqm` is
   tiny (the scripts spawn everything), so generating it means emitting the Arma config format with
   the right `addons[]`, the player slot class and the world. `dms_core.luaio` already does the
   same job for DCS. An Arma config emitter would sit next to `sqf.py`.
2. **description.ext generation.** The `DMS_site` param texts, `onLoadName`/`briefingName`, and the
   CfgDebriefing texts should come from the spec. Today the template check only catches a mismatch
   in the site count.
3. **Mod sets.** The user now wants mods. Each mod set needs:
   - a spec field (`mods: [...]`) that writes `addons[]` and the `-mod=` line for the harness
   - its own verified class list: a diag run with that `-mod` line, producing
     `classes-verified.<modset>.md`
   - the `fn_mods.sqf` pattern the other missions already use (soft-dependency detection)

   Modded classes are legal in the spec today but show up as *unverified*.
4. **Harness integration.** `tools/arma_harness/run_mission.py` should accept a spec, build it to
   a temp folder and run it headless. `test.expected` is already the PASS list, so the verdict can
   come straight from the spec. That is also the point where the Definition of Done applies: a
   generated mission is not done until it has run in Arma and been played.
5. **More templates.** `dms_hold`, `dms_ambush`, `dms_recon`, `dms_village` and `dms_baselife`
   each have their own `fn_config.sqf`. Each needs its own spec section, or a shared core plus
   per-template sections, before `template:` can take values other than `the_hill`.
6. **The DMS story layer.** Map the game-agnostic mission intent and arc (`dms_core.schemas`) onto
   `ArmaMissionSpec`, so the mission-designer skill can write Arma missions the same way it writes
   DCS ones. Keep story fields free of Arma specifics (ADR 0012).
7. **Positions.** Sites are still hand-measured (`kb/sites-verified.md`). A terrain catalog,
   like the DCS one, would let code pick sites from declarative intent (rule 6: LLMs write intent,
   code computes coordinates).
